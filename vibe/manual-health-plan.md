## Scope and fixed boundaries

The backend owns an authenticated, capability-gated immutable ledger for `health_report`, `health_observation`, and `health_restriction`; owner-scoped projection heads; as-of-watermark pages; exact raw-body operation replay; and the separate owner-scoped authorization receipt for the existing InBody AI action.

`records.kind='measurement'`, all generic `/v1/sync`, `/v1/sync/changes`, and `/v1/records` behavior, and existing body-measurement/InBody transport remain their own system of record. The health ledger must never copy, ingest, reference by name/date/value, deduplicate against, or emit a measurement. The feature adds no health provider, prompt, clinical interpretation, trainer access, profile export, or generic-record kind.

At implementation start the backend writer must compare the deployed/master changelog with the local unpublished PLAN-01 `010-training-proposals.sql`, then reserve the next append-only migration as **N+1**. `010` is not a promised health number. No published changeset may be edited; the concrete number and master include are frozen in the tracker before the first production edit.

## Data, transactions, and lock contract

`health_owner_state` is created only by an authenticated, accepted new health/disclosure mutation and holds the next owner `serverSequence` and shared `healthRevision`. `health_ledger_events` is the authoritative globally unique owner/revision index: a `VERSION` event identifies one first ingestion and a `HEAD` event identifies one immutable head-history transition. Immutable version and history rows retain their assigned event revision. Current-head rows are projections, never the source for an as-of page. Operation ledgers retain raw bytes, raw SHA-256 and exact response bytes; immutable version equality is a separately stored hash of the fixture's immutable tuple.

The normal write order is **health owner state → logical/current-head rows in lexical logical UUID order → immutable version/reference rows in lexical UUID order → operation or disclosure ledger → session/revocation**. A page locks owner state only long enough to freeze/read H and checks token ownership before querying immutable events. No health operation takes the catalog or generic sync-head locks.

Confirmed account deletion extends the existing prefix to **catalog → existing generic sync head → existing health owner state → health logical/head rows → health versions/events/operation/disclosure rows → user/session removal**. Preflight locks only existing state and then the user before consuming the code; a bad code rolls back without materializing health state or deleting data. The mutation path never locks `users` before health state, so it cannot invert deletion. Every write and the pre/post InBody check locks and verifies the caller's live session after the listed data locks.

For a new operation, duplicate/collision classification happens before parent/report checks. New parents must exist earlier in the request or already be stored for the same owner/logical/kind; forward/cyclic/cross-owner references fail as a whole. New observations and matching-CAS selection of an observation require a live confirmed resulting report head. Stored-equal versions and `ALREADY_CURRENT`/`STALE` outcomes deliberately bypass that present-day test as the fixture requires. A matching CAS appends history; a stale CAS retains an otherwise accepted version but does not rewrite the current head.

The first snapshot/changes request reads H atomically. Snapshot selects all version events `<=H` and exactly the latest head-history row per logical ID `<=H`; changes select every event in `(C,H]`. Both merge by immutable `healthRevision`, apply the 0..500 combined-event limit before splitting `versions` and `heads`, and issue a bounded signed token binding owner, mode, C, H and last emitted revision. Page tokens have a 24-hour TTL and cryptographic purpose separation from committed cursors. Committed cursors have no TTL while their history is retained. Signing uses existing server secret management; unavailable rotated keys or lost history are non-resumable. Expired page tokens, malformed, foreign, mode-mismatched, or non-resumable cursors return `410 health_cursor_expired` without mutation.

## Risks and explicit decisions

- Page tokens expire after 24 hours; committed cursors have no TTL while history is retained. Token purposes are cryptographically separated and use existing secret management; non-resumable history/key rotation returns `410 health_cursor_expired`. Test TTL boundary, purpose substitution, retained committed cursors after 24 hours and unavailable rotated keys.
- Health storage quota is configurable, default 200 MiB logical UTF-8 bytes per owner across stored versions, raw operations, stored results and history, plus 100000 versions. This is storage capacity, not AI usage limiting. Under the owner lock calculate the entire operation cost and reject `health_account_limit` atomically before event allocation; exact replay costs zero. T-002/T-003 own counters/allocation and T-005 tests tiny byte/count quotas, races, no partial writes/counter advance and free exact replay at capacity.
- Disclosure authorization is strictly owner-scoped and only gates AI-01 InBody. It grants no health sync, trainer/coach access, profile/notes access, or provider history context.
- Rollback after deployment is forward-only. Preserve immutable events, history and operation receipts; do not amend the migration or use cascading cross-owner cleanup.
