## Предлагаемая архитектура

Один модульный сервис: Kotlin + Spring Boot + Spring Security, PostgreSQL,
SQL-миграции Liquibase, Gradle Wrapper, REST JSON API `/v1`, контракт OpenAPI.
Совместимые стабильные версии закрепить при реализации. Kotlin выбран для близости
к Android-коду; Spring — для готовой поддержки безопасности, валидации и эксплуатации.
Работа с БД — явные SQL-запросы через Spring JDBC, транзакции на уровне сервисов.

Модули: auth, profile, catalog, gyms, routines, workouts, measurements, schedule,
sync, import. Все пользовательские данные привязаны к аккаунту; сервер определяет
его из сессии и проверяет принадлежность вложенных ссылок этому же владельцу.
Общий встроенный каталог отделён от пользовательских записей.

Android сохраняет Room для тренировок без сети. Каждое изменение и запись в outbox
сохраняются одной локальной транзакцией. WorkManager отправляет накопленное в backend,
получает изменения других устройств и применяет их в Room. Backend — каноническое
хранилище подтверждённых данных аккаунта. Локальный таймер и работающий экран тренировки
не зависят от доступности сервера.

## Вход и доступ

Согласованы оба способа входа: Google и email/пароль.

- Google: Android Credential Manager → ID token → проверка подписи, issuer, audience,
  срока действия и nonce на backend → аккаунт по `(provider, subject)` → собственная сессия.
- Если нужен email/пароль: регистрация, Argon2id, подтверждение email, вход,
  одноразовое восстановление и смена пароля. Нужен SMTP-провайдер; локально — тестовый SMTP.
- Не объединять Google и парольные аккаунты автоматически только по совпавшему email;
  связывание требует подтверждения владения существующим аккаунтом.
- Короткий access token (предлагается 15 минут) и случайный refresh token (30 дней),
  ротация refresh, хранение его хеша, обнаружение повторного использования, отзыв сессий.
  Android сериализует refresh-запросы, чтобы фоновые задачи не конфликтовали.
- Выход с текущего устройства, выход со всех устройств, список сессий, профиль,
  удаление аккаунта с повторным подтверждением личности.
- Ограничение частоты запросов к auth, ограничения размера и количества объектов,
  отсутствие паролей, токенов и содержимого замеров в логах.
- MVP: пользователь работает только со своими данными. Роли тренера, команды и
  отдельная административная панель не входят в базовый объём.
- В Android локальные данные, outbox и курсор принадлежат конкретному аккаунту;
  выход или переключение пользователя не должны отправлять историю другому владельцу.
  Присоединение ранее анонимных данных — отдельный подтверждаемый шаг миграции.

## API и модель данных

- `/v1/auth/*`, `/v1/me`, `/v1/sessions`.
- Каталог упражнений, мышцы и оборудование; пользовательские упражнения и залы.
- Программы, порядок упражнений, плановые подходы, привязки залов.
- Тренировки вместе с секциями, подходами и историческим контекстом.
- Замеры со всеми nullable-полями текущей модели InBody и ручных обхватов.
- Расписание с часовым поясом и стабильными ID; внешние Calendar event ID
  остаются атрибутами интеграции, а не идентификаторами серверных объектов.
- Отдельные DTO от Room, строгая валидация, ограничения пагинации, единый формат ошибок.
- UUID сохраняются при импорте; числовые локальные связи преобразуются в UUID.
  Повторяющиеся секции одного упражнения сохраняются отдельно по sectionId.

## Синхронизация

- Push изменений с уникальным operationId и базовой серверной revision.
- Повтор одной операции возвращает прежний результат без дублей; повтор operationId
  с другим телом отклоняется. Идемпотентность привязана к владельцу.
- Запись агрегата атомарна: тренировка с секциями и подходами, программа со связями.
- Изменения выдаются страницами по серверному курсору. Порядок фиксации изменений
  должен исключать пропуски при конкурентных транзакциях; одного sequence ID недостаточно.
- Удаления распространяются через tombstone. Предусмотреть полный повторный sync
  при истечении срока хранения курсора и защиту от восстановления удалённых данных.
- Конфликт revision возвращает 409 и серверную версию. Локальная правка остаётся в
  очереди до разрешения конфликта; часы устройства не определяют победителя.
- При двух устройствах конфликтующие правки не должны молча затирать друг друга.
  Для первой версии достаточно явного выбора версии пользователем с сохранением
  обеих версий до выбора; автоматическое слияние подходов не требуется.
- Проверить потерю ответа после успешного commit, повторы, перезапуск приложения,
  параллельные записи, пагинацию и удаление офлайн.

## Перенос данных и отказ от Sheets

Согласовано: Sheets удаляется из production-интеграций. Источником первичного переноса
служит локальная Room. Данные, которые существуют только в старой таблице, нужно вернуть
в локальную базу старой версией приложения до обновления. Backend к таблицам не обращается.

Первый вход требует подтверждения привязки локальной истории к аккаунту. Синхронизация
сохраняет UUID и связи, повторяет неподтверждённые запросы и сообщает о конфликтах.
Исходную базу можно экспортировать в SQLite до входа и переключения аккаунта.
Экспорт в Excel (.xlsx) — отдельная будущая задача, не входит в MVP.

## Минимальная инфраструктура

- Существующий VPS Ubuntu 24.04, 62.84.122.55, пользователь valerochka, Docker Compose; ориентир для старта — 2 vCPU / 4 GB RAM,
  окончательный размер определить после замера. Провайдера и платные ресурсы не создавать
  в рамках согласования плана.
- Контейнеры backend и PostgreSQL, существующий системный Nginx; приложение и БД в закрытой Docker-сети,
  наружу только HTTP/HTTPS и административный SSH.
- `api.valerochkagym.tech` направить на VPS; Nginx использует существующий TLS-сертификат и таймер Certbot.
- Dev/prod-конфигурации, `.env.example` без секретов, постоянные volumes,
  health/readiness probes, лимиты ресурсов и ротация логов.
- Скрипт первоначальной настройки сервера и подробная инструкция запуска.
- Ежедневный backup PostgreSQL, настраиваемое хранение копии вне VPS,
  документированный restore и тест восстановления в отдельную БД.
  Цель для MVP — потеря не более суток данных при потере сервера; фактическое время
  восстановления измерить. Для внешней копии потребуется выбранное хранилище.
- Структурированные технические логи с request ID, закрытые метрики, внешний
  health-check с уведомлениями после выбора получателя/сервиса владельцем.
- Одна машина допускает простой при аварии и короткое прерывание при обновлении;
  высокая доступность не входит в минимальную инфраструктуру.

## CI/CD

GitHub Actions в backend-репозитории:

1. PR: форматирование/статический анализ, unit-тесты, интеграционные тесты на настоящем
   PostgreSQL через Testcontainers, проверка миграций и API-контракта, сборка Docker image.
2. Main после успешных проверок: публикация образа в GHCR с SHA коммита и digest.
3. CD: последовательный deploy проверенного digest по SSH на VPS, backup перед миграцией,
   миграции, запуск, ожидание readiness и внешний smoke-check HTTPS.
4. При сбое приложения — возврат предыдущего образа, совместимого со схемой.
   Миграции выполнять обратно совместимо; откат образа не означает откат БД.
   Разрушительные миграции требуют отдельного сценария обслуживания и восстановления.
5. Возможность ручного повторного deploy проверенной версии. Секреты в GitHub environment
   и на сервере, минимальные права workflow, SSH host key закреплён.
6. Изменения только документации проходят лёгкий обязательный статус; изменения кода,
   сборки и инфраструктуры запускают соответствующие проверки. CI-конфигурация не должна
   пропускать свою собственную валидацию. Падающие тесты блокируют publish/deploy.

Обязательные тесты: изоляция двух пользователей и вложенных ссылок, истёкшие/поддельные
токены, refresh rotation/reuse/logout, валидация агрегатов и транзакционный rollback,
повторы sync/import, конфликты и конкурентная пагинация, tombstone, миграции БД,
восстановление backup. Google и SMTP в CI заменены управляемыми тестовыми адаптерами;
проверка подписи тестируется локальными ключами, без реальных аккаунтов.

## Этапы и результат

1. Согласовать решения ниже и уточнить OpenAPI/таблицы относительно актуальной Android-базы.
2. Создать каркас, dev Compose, SQL-миграции и сразу включить CI с тестовой БД.
3. Реализовать вход, управление сессиями и разграничение доступа с тестами.
4. Реализовать предметное API, sync и импорт с тестами целостности и конфликтов.
5. Подготовить production Compose, Nginx, backup/restore, CD и эксплуатационные инструкции.
6. Если Android входит в задачу: добавить API-клиент, account-scoped Room/outbox,
   миграции, auth UI, замену воркеров и переход с Sheets; прогнать полный Android
   testDebugUnitTest и assembleDebug, увеличить версию по правилам репозитория.
7. Локально проверить полный сценарий и restore; после предоставления инфраструктуры
   выполнить согласованный deploy и проверить реальный домен.

Готовность: пользователь входит, видит только свои данные, выполняет тренировку офлайн,
после сети она сохраняется на сервере и восстанавливается на другом устройстве без дублей;
CI блокирует неисправный релиз, CD ставит прошедший тесты образ, backup восстанавливается.
Если согласован только backend, сценарий двух клиентов проверяется API-тестом,
а переключение реального приложения остаётся явно незавершённым этапом интеграции.

## Зафиксированные решения и остающиеся зависимости

- Liquibase; Google и email/пароль; подключение Android входит в MVP.
- Sheets полностью убран из рабочих HTTP-интеграций. Excel позже.
- Calendar и AI остаются на Android; API backend их не проксирует.
- Развёртывание на существующем Ubuntu VPS, через существующий Nginx/Certbot.
- SMTP пока не предоставлен: отправка кодов в production отключена явно.
- Хранилище backup вне VPS и внешний получатель уведомлений пока не выбраны.
- Автоматическая проверка разрешений отклонила добавление постоянного SSH-ключа
  GitHub Actions с sudo и включение production CD. Для этого требуется явное согласие.
- Push Android-ветки требует явного запроса по AGENTS.md; пока обе ветки локальные.
