# Стандартный каталог и переход Android

## Контракт

`GET /v1/catalog` публичен. Ответ содержит `active`, `revision`, `records`, `equipment`.
Каждая запись: `kind`, `id`, `revision`, `archived`, `payload`. Для упражнения, зала и
шаблона `id` — UUID, для оборудования — прежний строковый ID. Оборудование содержит
`name`, `group`, `synonyms`, `provides`. Покрытие определяется прямым вхождением в
`provides`, без транзитивного расширения. Архивные записи сохраняются в полном снимке.

ETag имеет вид `"catalog-<revision>-<active>"`. `If-None-Match` возвращает 304.
Чтение держит shared lock строки `catalog_state`; редактирование и перенос — exclusive lock.
Каталог и личные sync heads имеют независимые ревизии. Все операции с обеими областями
берут блокировки в порядке каталог → личный sync head. Проверка версии клиента
повторяется под блокировкой каталога, поэтому конкурентная активация безопасна.

`/v1/sync`, `/v1/sync/changes`, `/v1/records/**` сохраняют личный контракт. Новый клиент
передаёт `X-Gym-Sync-Version: 2`, а push дополнительно содержит `catalogRevision`.
После активации старые клиенты получают `426 client_update_required`.
UUID общих объектов запрещены для личной записи (`403 standard_read_only`).
Зависимые записи со старой ревизией каталога получают `409 catalog_stale`.
Повтор уже подтверждённого `operationId` возвращает прежнее подтверждение; новое
содержимое с тем же ID получает `409 operation_reused`.

Существование ссылок проверяется для всего результирующего графа. Общие записи могут
ссылаться только на общий граф. Личные — на собственные и общие объекты. Покрытие
оборудованием проверяется при изменении конфигурации упражнения/зала, программы или
активной тренировки. Обновление общего оборудования не заставляет заново валидировать
все неизменённые личные программы при отправке несвязанных данных.

## Администрирование

Раздел «Стандартный каталог» не требует выбора владельца:

- `GET /admin/api/standard?kind=exercise|gym|routine|equipment&q=&archived=false&offset=0&limit=50`;
- `GET /admin/api/standard/{kind}/{id}`;
- `PUT /admin/api/standard/{kind}/{id}` с `operationId`, `baseRevision`, `reason`, `payload`;
- `POST /admin/api/standard/{kind}/{id}/archive` с `operationId`, `baseRevision`, `reason`, `archived`.

У новой записи `baseRevision=0`. Редактор шаблона задаёт упражнения, порядок,
отдых, плановые подходы и залы. Архив скрыт из нового выбора; существующие ссылки
продолжают разрешаться. Аудит содержит автора, причину и состояния до/после,
`user_id` общих действий равен NULL. Удаление аккаунта не удаляет общий каталог.

## Подготовка и применение

Структурные changesets 005 и 006 создают независимые таблицы, допускают NULL владельца
аудита и заполняют 61 определение оборудования из Android. Пользовательские строки
Liquibase не переносит. Начальное `catalog_state.active=false`.

1. Развернуть backend. Проверить `/v1/catalog`: `active=false`.
2. Установить новый Android. Дождаться первоначального заполнения локальных требований
   оборудования и карт мышц, завершить текущую тренировку и личную синхронизацию.
   До переноса baseline/outbox должны быть согласованы с сервером.
3. Выполнить и проверить резервную копию штатными `scripts/backup.sh` и
   `scripts/verify-restore.sh`. На время применения прекратить административное
   редактирование исходного аккаунта; команда сама сериализуется с sync.
4. Передать команде обычные переменные подключения backend и выполнить проверку:

   ```bash
   scripts/migrate-catalog.sh check --gym.catalog.source=SOURCE_UUID
   ```

   Если аккаунт единственный, `source` можно опустить. При нескольких аккаунтах UUID
   обязателен. Проверка возвращает количество упражнений, залов и сохраняемых личных
   записей; транзакция проверки откатывается.
5. После проверки выполнить:

   ```bash
   scripts/migrate-catalog.sh apply \
     --gym.catalog.source=SOURCE_UUID \
     --gym.catalog.actor=ADMIN_UUID \
     --gym.catalog.reason='Перенос стандартного каталога' \
     --gym.catalog.backup-confirmed=true \
     --gym.catalog.client-ready=true
   ```

   Флаги подтверждают уже выполненную подготовку, а не выполняют backup или клиентский sync.
   Автор должен быть подтверждённым администратором. `GYM_JAR` позволяет указать путь к JAR.
   Команда запускает временный HTTP listener на случайном порту и закрывает приложение
   после результата; секреты не передаются аргументами командной строки.

Одна транзакция переносит действующие упражнения и залы с исходными UUID и JSONB,
удаляет только эти личные строки, пишет аудит, увеличивает каталоговую ревизию и
активирует протокол. Личные шаблоны, тренировки, замеры, расписание и подтверждения
прошлых операций сохраняются. Ошибка откатывает всё. Повтор возвращает `already_active`.
Совпадение UUID с уже созданной общей записью или с другой личной записью (в том числе другого аккаунта) требует устранить конфликт до применения.

## Android и проверка выпуска

Room 15→16 — ручная миграция, без destructive fallback. Поля `origin`/`archived`
добавлены к упражнениям, залам и шаблонам; `catalog_state`, `catalog_records`,
`catalog_equipment` отделены от `backend_baseline`/`backend_outbox`.
Каталог загружается до личных данных и без аккаунта. Активная тренировка откладывает
его применение. Обновление по UUID сохраняет локальные ID и исторические связи.

При неподтверждённых правках перенесённого объекта сохраняются исходный outbox и
снимок перехода. В настройках аккаунта пользователь выбирает личные копии или стандартные
версии. Выбор переживает перезапуск; копии получают новые UUID, история остаётся на
прежних ссылках. Неизменённые и неиспользуемые APK-заготовки на чистой установке
не отправляются как новые личные упражнения после получения активного каталога.

Рабочие проверки оборудования читают проекцию локальной таблицы; встроенные определения
используются для первоначального офлайн-заполнения. Повторное открытие базы не меняет
загруженные правила или карты мышц. SQLite-защита запрещает личные изменения стандартных
родителей и вложенных конфигураций. Экспорт полной SQLite-базы включает происхождение,
каталог и журнал перехода. Очистка удаляет личные данные, сохраняя общий каталог.

Перед выпуском выполнить:

```bash
./gradlew check bootJar
npm test
# В Android-проекте:
./gradlew spotlessCheck :app:testDebugUnitTest :app:assembleDebug
```

Для Colima тестовый запуск backend использует `DOCKER_HOST` на сокет Colima и
`TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`.
Проверки покрывают JPA-регрессии, публичный ETag, аудит/повторы/архив, атомарный перенос,
Room 15→16, локальные ID и историю, конфликт outbox после перезапуска, публичное обновление
оборудования, отсрочку при активной тренировке и Compose accessibility-действие копирования.

После применения проверить восстановление аккаунта на чистой установке, количество
тренировок и подходов, объём, рекорды, историю упражнений и нагрузку по мышцам. Затем
повторить sync и открыть приложение заново. Production-перенос выполняется только
после проверки резервной копии; для отмены применённого переноса требуется восстановить
согласованную резервную копию backend и соответствующее состояние клиента, а не вручную
переключать `active=false`.
